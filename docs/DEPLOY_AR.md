# تشغيل مسار من المتصفح — بدون Terminal على جهازك

## 1. ارفع المشروع إلى GitHub

1. فك ZIP على جهازك.
2. في GitHub أنشئ مستودعاً خاصاً Private.
3. اختر **Add file → Upload files** وارفع محتويات مجلد `masar-v13`، بحيث يوجد `package.json` و`render.yaml` في جذر المستودع، ثم **Commit changes**. GitHub لا يفك ZIP؛ ارفع محتوياته.
4. ارفع أيضاً `.github/workflows/check.yml` إذا لم يظهر المجلد المخفي في اختيار الملفات. هذا لتشغيل الفحص التلقائي؛ ليس شرطاً لتشغيل التطبيق.
5. لا ترفع ملفات `.env` أو جلسة WhatsApp القديمة. الحزمة المرفقة لا تحتوي عليها.

## 2. جهّز Supabase مرة واحدة

يمكن استعمال مشروعك الحالي للحفاظ على بيانات النسخة السابقة أو مشروع جديد. خذ نسخة احتياطية قبل أي ترحيل.

1. افتح الملف `supabase/001_masar.sql` في GitHub وانسخ النص بالكامل.
2. في Supabase افتح **SQL Editor → New query**، الصق النص واضغط **Run**. لا تشغل ملفات ترحيلات النسخة القديمة مع هذه الحزمة. الترحيل الجديد لا يعدلها أو يحذفها.
3. في **Authentication → Users → Add user** أضف بريدك وكلمة مرور قوية مع تأكيد البريد. هذه بيانات تسجيل دخول اللوحة.
4. في SQL Editor شغّل الآتي بعد استبدال البريد ببريد المستخدم الذي أنشأته:

```sql
insert into public.masar_staff (user_id)
select id from auth.users where lower(email) = lower('YOUR_EMAIL@example.com')
on conflict do nothing;
```

5. راجع وجود المستخدم في جدول `masar_staff`. إضافة مستخدم إلى Authentication وحدها لا تمنحه صلاحية إدارة المشروع.
6. من إعدادات المشروع احتفظ بـ **Project URL** و**anon public key** للواجهة و**service_role key** لخدمة البوت. المفتاح الأخير للخادم فقط ولا يوضع في Vercel أو كود الواجهة.

## 3. انشر الواجهة على Vercel

1. اختر **Add New → Project → Import Git Repository** وحدد مستودع المشروع.
2. اجعل Root Directory هو جذر المستودع. إعدادات البناء موجودة في `vercel.json`.
3. أضف Environment Variables التالية:

| الاسم | القيمة |
|---|---|
| VITE_SUPABASE_URL | عنوان مشروع Supabase |
| VITE_SUPABASE_ANON_KEY | المفتاح العام anon |
| VITE_BOT_API_URL | مؤقتاً `https://example.invalid` لحين إنشاء خدمة البوت |

4. اضغط **Deploy** واحتفظ بعنوان الإنتاج مثل `https://your-masar.vercel.app`. لن تكتمل قراءة البيانات قبل خطوة خدمة البوت. متغيرات `VITE_` تدخل أثناء البناء؛ تغييرها يحتاج **Redeploy**.

## 4. انشر خدمة البوت على Render

1. افتح Render واربط GitHub، ثم **New → Blueprint** وحدد نفس المستودع. سيقرأ `render.yaml` ويجهز خدمة Docker والقرص الدائم.
2. راجع تكلفة الخطة المعروضة قبل تفعيلها. الجلسة تحتاج خدمة دائمة وقرصاً دائماً؛ لا تستخدم نسخة تنام أو تمسح الجلسة عند إعادة التشغيل.
3. أدخل القيم المطلوبة:

| الاسم | القيمة |
|---|---|
| SUPABASE_URL | نفس عنوان Supabase |
| SUPABASE_SERVICE_ROLE_KEY | مفتاح service_role السري؛ على Render فقط |
| DASHBOARD_ORIGIN | رابط إنتاج Vercel كاملاً، بدون `/` في النهاية |

4. ملف Docker يثبت Chromium ويشغّل الخدمة تلقائياً. القرص في `/data`، والجلسة في `/data/whatsapp`. لا تغيّر المسارات أو عدد النسخ؛ استخدم instance واحدة.
5. بعد اكتمال النشر انسخ عنوان الخدمة `https://…onrender.com`. افتح `/health` عليه؛ المفترض أن يظهر `{"ok":true}`.
6. ارجع إلى Vercel وعدّل `VITE_BOT_API_URL` إلى عنوان Render بدون `/` في النهاية، ثم **Redeploy**.
7. إذا أضفت نطاقاً للواجهة، عدّل `DASHBOARD_ORIGIN` في Render. يمكن السماح بعدة عناوين بفواصل. لا تستخدم `*`، ولا تحتاج عنوان Render داخل القائمة.

## 5. شغّل كل شيء من اللوحة

1. افتح رابط Vercel وسجل دخولك بالبريد وكلمة المرور اللذين جهزتهما.
2. لو تستخدم نفس Supabase القديم، افتح **الإعدادات → استيراد البيانات القديمة** وانتظر ظهور النتيجة. يمكن إعادة الاستيراد؛ لا يعيد إنشاء السجلات الموجودة. خليك في الصفحة حتى تظهر النتيجة.
3. راجع **أسئلة البوت**: رتّبها، واختر نوع الإجابة الصحيح، وحدد المطلوب. إن لم توجد أسئلة، اضغط **إضافة الأسئلة الأساسية**. عدّل سؤال المستند وفعّله فقط عند تحديد المطلوب فعلاً.
4. راجع **مناطق العمل** واكتب التفاصيل الصحيحة لكل منطقة؛ لا يوجد افتراض لمرتب أو موعد.
5. راجع **الإعدادات** ورسالة الترحيب والإكمال، وتأكد أن «الفهم الذكي المحلي» مفعّل إذا كنت تريد فهم الردود غير المباشرة.
6. أوقف عملية البوت القديم قبل ربط الجديد. في **ربط واتساب** اضغط **ربط واتساب**، ومن الموبايل افتح **الأجهزة المرتبطة → ربط جهاز** وامسح QR.
7. بعد ظهور **متصل وجاهز** أرسل من رقم اختبار آخر وأكمل الرحلة؛ ستجد ملفه في **المتقدمون**.
8. زر **فصل الاتصال** يلغي الجلسة. الربط التالي يعرض QR جديداً. غلق صفحة الويب لا يفصل البوت.

## بعد النشر: فحص فعلي قصير

- أرسل تحية، ثم اسم وعمر أو الأسئلة التي اخترتها. تأكد من حفظ كل جواب بالاسم الصحيح.
- أثناء سؤال آخر أرسل «تفاصيل الشغل في أكتوبر؟»؛ يجب أن تأتي التفاصيل المسجلة ولا يتحرك السؤال دون إجابة.
- جرّب «لسه مجبتش موتوسيكل» على سؤال نعم/لا؛ يجب أن يسجلها الفهم المحلي «لا»، ولو كانت صياغة غامضة يطلب توضيحاً.
- أرسل صورة اختبار أو PDF إذا عندك سؤال مستند. افتح المرفق من ملف المتقدم.
- تأكد أن الرقم الظاهر هو رقم المرسل؛ LID غير القابل للحل يظهر غير متاح. جرب جهة اتصال غير محفوظة أيضاً.
- أكد حضور المحاضرة ثم بدء العمل من ملف متقدم مكتمل، وراجع التقرير.
- افصل وأعد الربط. أعد تشغيل Render من لوحة الخدمة وتأكد من استعادة الجلسة دون QR إذا لم تفصلها.

## لو ظهر خطأ

- **الحساب غير مصرح له:** أضف UUID المستخدم إلى `masar_staff` كما في الخطوة 2.
- **تعذر إتمام العملية:** تحقق أن SQL نُفّذ بالكامل، ومفاتيح Render صحيحة، وراجع Logs في لوحة Render.
- **Failed to fetch / لا تصل الخدمة:** تحقق من `VITE_BOT_API_URL` و`DASHBOARD_ORIGIN`، ثم أعد نشر Vercel بعد تعديل متغيراته.
- **QR لا يظهر:** انتظر تجهيز المتصفح، ثم راجع حالة الخدمة. جرب الفصل وإعادة الربط من الصفحة.
- **فهم الإجابات لا يعمل:** تأكد أن خيار الفهم الذكي المحلي مفعّل من الإعدادات. الردود الغامضة عمداً تطلب توضيحاً بدل التخمين.
- **إرسال غير مؤكد:** افتح واتساب أولاً لتتأكد هل وصل الرد. أعد المحاولة من سجل الرسالة فقط بعد المراجعة، لتجنب تكرار الرسالة.
- **مستورد لكن رقم غير متاح:** بعض النسخة القديمة كانت تحفظ LID بعد حذف اللاحقة؛ لا يمكن اعتباره رقم هاتف. الربط الصحيح يعتمد على وصول رسالة جديدة وإتاحة واتساب للرقم الحقيقي.

## حدود الاستضافة والتكامل

الربط بالـQR يستخدم `whatsapp-web.js` وليس Meta Cloud API؛ يعتمد على WhatsApp Web وقد يحتاج تحديثاً إذا تغيرت واجهته. خدمة البوت لا تُنشر كـVercel Function في هذه الحزمة. يمكن نقل Docker إلى استضافة أخرى تدعم عملية مستمرة وقرصاً دائماً، مع الحفاظ على نفس الإعدادات.
