# Agent CRM Tools — Phase 2

## النتيجة
أدوات عمل حقيقية مقيدة بالصلاحيات للـ Agent في مسار WhatsApp: لا تعتمد على نص حر من LLM لتحديد اسم أداة أو بيانات مستخدم؛ اختيار الأدوات والباراميترات من رسائل المتقدم المعنية فقط، وبيانات المتقدم/المكتب/المناطق/المعرفة من `config(db, office_id)` و `loadKnowledge(db, office_id)` الخاصة بالمكتب.

| Tool | المصدر | المهمة | يغيّر البيانات؟ |
| --- | --- | --- | --- |
| `read_candidate_progress` | أسئلة وأجوبة المتقدم | عدد الأسئلة المكتملة، السؤال الناقص، حالة التقديم الفعلية | لا |
| `read_area_details` | `masar_areas` | نص التفاصيل المسجّل حرفيًا لو المنطقة ونظام التشغيل محددين | لا |
| `compare_registered_areas` | `masar_areas` + Area Advisor | مقارنة ماركت/مطاعم في **نفس المنطقة** أو بين منطقتين محددتين | لا |
| `find_nearest_work_areas` | Geoapify أو التقدير المحلي | أقرب مناطق تشغيل فعّالة، مع توضيح نوع المسافة ومصدرها | لا |
| `search_verified_knowledge` | `masar_knowledge` | معلومات المكتب المؤكدة فقط، وإلا يطلب توضيحًا من مسؤول | لا |

## إدارة طلب فيه عدة أسئلة
المدخل: «أنا ساكن في عين شمس، قارن الماركت والمطاعم وقولي الأقرب للشغل».

الخطوات:
1. تحديد `find_nearest_work_areas` حسب رسالة المتقدم. يحصل على 3 ترشيحات من المناطق النشطة والمؤهلة، دون اختيار.
2. استخدام أقرب **منطقة لها بيانات تشغيل مسجّلة** سياقًا للمقارنة؛ `compare_registered_areas` يقارن نظامي الماركت والمطاعم في نفس المكان، ويعرض النص الأصلي منهما لو وجد النظامان.
3. الرجوع لسؤال التقديم المعلّق بعد إجابة الأسئلة الجانبية.
4. يتم تخزين سياق الترشيح/المقارنة فقط، وليس `preferred_work_area`، ولا تعديلات على Qualification.

مثال تاني: «تفاصيل ماركت العبور وناقصني إيه؟» → تقدم التقديم + التفاصيل المكتوبة حرفيًا + Preview فقط، دون موافقة أو تثبيت.

## حدود الأمان
- **Read-only tools**: الأدوات لا تملك وصولًا لكتابة/تغيير/حذف بيانات أو إرسال WhatsApp أو قبول/رفض مرشح. التأكيد النهائي واختيار المنطقة والتأهيل والـ handoff يعتمدون على قواعد `flow.js` الحالية.
- المخرجات بتتجاوز Response Composer حتى لا يعيد الـ LLM صياغة الأرقام/المرتبات أو يحذف المصدر الجغرافي.
- قائمة الأدوات المسموحة ثابتة. الاختيار يتم من نية المتقدم المدقّقة، حتى لو حاول LLM اختراع أسماء أدوات.
- حد أقصى **3 أدوات** لكل رسالة مركبة؛ لا توجد حلقة ذاتية متكررة أو تسلسل غير محدود.
- مناطق مكتب تاني ومعرفته مستبعدة حسب `office_id`. المناطق غير المفعّلة والمعرفة القديمة/المتعارضة مستبعدة.
- لو المكان مش معروف، البوت يسأل عن حي السكن بدل اختراع طريق أو وقت مواصلات. مسافة الطريق التقديرية ليست ضمانًا لزحمة المرور.
- يتم تسجيل أسماء الأدوات ونجاحها في `masar_events`، وتظهر في `masar_agent_decisions.intents` بصيغة `tool:name`، بدون إضافة بيانات شخصية لهذه المؤشرات.
- الأدوات لا تعمل لما `ai_enabled=false`، وممكن إيقاف المسار ب`agent_crm_tools_enabled=false` ضمن إعدادات runtime لو متاح. لم نضف أعمدة قاعدة بيانات جديدة.
- لا تحتاج لمفتاح LLM إضافي. خدمة Geoapify تستخدم مفتاحها الموجود مع الحدود والكاش المُطبقة سابقًا.

## الاختبار
```bash
npm test
npm run build
```

الاختبارات داخل `whatsapp-bot/test/crm-tools.test.js` تغطي الطلب المركّب، غياب موقع السكن، نص التفاصيل الأصلي، عدم تثبيت منطقة العمل، الإجابات الناقصة، منع إدعاءات القبول، قيود المكتب، منع المعرفة غير الموثوقة، وفشل الأداة بدون تعطل المحادثة.

بعد نشر Railway وظهور SUCCESS، اختبر رسائل مثل:
- «أنا ساكن في عين شمس، قارنلي الماركت والمطاعم ورشحلي الأقرب»
- «قولّي تفاصيل ماركت العبور وحالة طلبي وصلت لفين»
- «أنا ناقصني إيه في التقديم؟»
- «محتاج أعرف أقرب منطقة بس» (المسار القديم يعمل بصورة طبيعية)

المرحلة الثالثة المقترحة: مركز جودة Agent يقيس دقة الإجابات، يحاكي مئات الحالات ويعرض نسبة الأدوات الناجحة، أسباب الـ handoff وتكلفة كل محادثة.
